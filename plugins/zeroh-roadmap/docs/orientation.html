zeroh-roadmap in one sitting

An orientation for engineers, written against the framework you probably already know (obra's superpowers). Ten minutes, no marketing. Sources: the skills and CLI in this repo, the 2026-08 skill gauntlet, and a superpowers v6.3.0 comparison.

TL;DR: superpowers is a methodology in prompts — composable skills that teach an agent a good process and trust it to comply. zeroh-roadmap is a delivery machine — typed plans on disk, a CLI that owns the mechanics, refusal-based enforcement where superpowers has persuasion, and an independent judging + eval layer superpowers doesn't attempt. Superpowers optimizes a session; this plugin optimizes a program of work across many sessions, models, and weeks — including ones where nobody is watching.

The one distinction that generates the rest

Both systems answer the same question — how do you stop an LLM agent from confidently shipping garbage? — with opposite bets:

  • SUPERPOWERS  The agent will comply if you tell it clearly. So: write excellent instructions (brainstorm → plan → TDD → review), inject them at session start, and phrase them as "mandatory workflows, not suggestions". Enforcement is rhetorical.
  • ROADMAP  The agent will eventually fail — degrade, hallucinate a "done", skip a gate — so make the failure modes structurally hard. Enforcement is mechanical: a CLI that refuses, hooks that block, schemas that reject.

Concretely, in this plugin: roadmap gate run --verify-complete refuses a done-flip whose gate report carries no recorded review rounds. roadmap result check parses an executor's return against a typed contract — prose is never trusted. A Stop-hook blocks a phase-executor from ending its turn with anything except tool calls or the typed result. Policy writes 409 on version races. executor-arm makes two executors on one phase structurally difficult. None of these can be talked out of the way, which is the point: the model's eloquence is exactly what you can't trust when it's wrong.

What it is, mechanically

Three typed artifacts and one loop.

roadmap/
├─ backlog.ts              the active queue (a TypeScript module, parsed + validated)
├─ arcs/<ID>.arc.ts        an ARC — a contract: planes, acceptanceCriteria, honestyRails, singleSeams, designRefs
├─ phases/phase-N.phase.ts a PHASE — a KNOWN DIFF: tasks with file-level steps, runnable assumption tripwires,
│                          per-task acceptance criteria, testMode; decisions pre-made at plan time
└─ roadmap.config.json     the consumer bindings: gate commands, validation tiers, judge model, merge policy
plan-arc→queue→do-arc→ arc-sweep→validate-arc→ land→eval
  • plan-arc settles the design before any phase exists (architect ∥ UX designer search the consumer's canon, the human confirms; the confirmed design becomes a contract). Each member phase is then authored to the known-diff bar and independently reviewed until READY.
  • do-arc drives one deterministic loop: roadmap arc next hands back exactly one action, re-derived from git + the phase files every time — so a dead session resumes by just re-entering the loop. Mid-size phases delegate to a phase-executor subagent (armed, watched); every non-done exit is a typed halt (escalated, self-descope, checkpoint, blocked, stalled, unobserved) with an owner, never a shrug.
  • do-phase is the unit underneath: one task = one commit, TDD with a test-engineer that never sees the implementation steps, an architect Decision Contract at every convenient-vs-proper fork (PROCEED_WITH_FIX or ESCALATE_TO_USER — no third path), then a gate: quality-pass sweep, code-reviewer rounds capped at 5, design-parity when a UX contract is in play.
  • validate-arc is the layer superpowers doesn't have an analogue for: one independent intent-validator judge per acceptance criterion, forbidden from reading the diffs, driving the real shipped flow and returning evidence-backed verdicts. PASS lands (autonomously, per merge policy); GAPS triggers a bounded corrective loop.
  • eval closes the flywheel: a pinned judge model scores every landed arc against a rolling baseline; lessons are captured at the moment they happen; the skills themselves were competitively regression-tested (the 2026-08 gauntlet: blind trials, sealed held-out sets — ~40% of nice-looking rewrites turned out to be regressions only blind trials caught).

The cast — who does what, on which model

The plugin is multi-agent AND multi-vendor. Nine specialist agents carry the judgment seams; a governed Codex delegation lane carries whole phases on a second vendor. Frontmatter models are defaults — the consumer's modelPolicy.judgeModel upgrades every judge seam at spawn time (this fleet runs judges on fable).

Why the model column matters: every artifact records who produced it — plannedBy.model on the phase, a model stamp on every recorded gate round, the executor's driver (model + lane) in its typed result, the validate panel's actual judgeModel, and the eval judge's pin. The arc-evals slice on exactly these stamps, so "which LLM is good at which seam" is a measured question here, not a vibe: a phase planned by fable, built by opus, delegated to gpt-5.6-sol, and judged on the pin all leave attributable evidence, and a model swap shows up in the baseline instead of being argued about.

Honest trade-offs

Adoption costOne install, works in any repo/language, value in minutes TS + zod consumer, roadmap/ scaffold, config bindings, a real learning curve
EnforcementPrompt discipline + session hook; a lazy model can skip any step CLI refusals, typed contracts, Stop-hooks, 409s — misbehavior is structurally hard

Verification"Is this code good?" — reviewer per task "Does the shipped product do the job, at the bar set?" — independent judge per criterion, evidence required
SessionsOne developer, one session, human checkpoints Fleet-aware: lanes, claims, cross-repo collision preflight, liveness verdicts, lossless resume
Token costLow — aggressively compressed skills Planning is genuinely expensive; it buys unattended execution (and is being leaned further — phase 2420)
Portability8+ harnesses (Claude Code, Cursor, Codex, Devin…) Orchestration is Claude-Code-native; execution is already multi-vendor — the governed Codex lane runs (and plans) whole phases on gpt-5.6-sol, and every artifact records which model did what (see "The cast" below)
MaintenanceActive OSS community, MIT One team; survives model drift via its own measured eval loop, not via crowd testing

Two genuine gaps this plugin has that superpowers covers: a brainstorming protocol (Socratic idea refinement before anything is planned) and a systematic-debugging skill (structured root-cause when an executor hits a gnarly bug). Both are a recorded evaluation — roadmap/followups/DEBUGSKILL.md in the flagship consumer names the candidate plug-in seams, an extent ladder, and the evidence bar (adopt only where the model demonstrably fails without it; the gauntlet showed commodity methodology is deletion fodder). Interesting convergence signal: superpowers' 2026 releases are independently rediscovering this plugin's decisions — scaled ceremony by task complexity (≈ execution bands), plan-scoped workspaces (≈ the worktree lane), review-fix loops that resume the implementer (≈ gate rounds).

When to reach for which

  • Use superpowers for a fresh repo, a non-TS stack, a quick project, or any environment where you'll be watching the agent work. It's a very good floor, cheap to adopt.
  • Use zeroh-roadmap when the work is a program, not a task: multi-week arcs, multiple concurrent sessions on shared checkouts, autonomous overnight execution, and any codebase where a plausible-but-wrong "done" is expensive. The planning tax is the price of not supervising.
