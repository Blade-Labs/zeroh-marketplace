# Useful documentation

Keep one canonical home per fact and link to it. Explain the as-built behavior and non-obvious reasons; do not duplicate code or a session transcript. Record a separate architectural decision only when the tradeoff has lasting value or the user asks.

Use concise product-facing instructions. Small projects may keep architecture, test strategy and run commands in README/AGENTS guidance. Do not create empty documents to fill a template list. Keep check results and unresolved work with typed progress or the PR; they do not need a permanent proof archive.

Refresh stale guidance when the changed behavior makes it wrong. Verification records may legitimately name dates, versions and exact commits; do not erase useful provenance in pursuit of timeless wording.
